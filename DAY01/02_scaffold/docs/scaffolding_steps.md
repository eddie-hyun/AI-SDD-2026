# MyHub 개발 여정 — 전체 타임라인

Step 1 ~ 7로 구성되어있습니다.

```
Step 1   브라우저 ──▶ 백엔드 서버 ──▶ Supabase (PostgreSQL)
                                      "서버가 DB랑 진짜 대화하는지" 확인

Step 2   브라우저 ──▶ 백엔드 서버 ──▶ profile 테이블 ──▶ JSON 응답
                                      내가 넣은 데이터가 웹 주소로 나옴

Step 3   React(:5173) ──Vite 프록시──▶ 백엔드 서버 ──▶ Supabase
             OpenAPI 스펙 ──자동 생성──▶ TS 타입
                                      JSON 을 사람이 보는 화면으로

Step 4   브라우저 ──로그인, 서명된 쿠키──▶ 백엔드 서버 ──▶ PUT /api/profile
                                      화면에서 직접 로그인해서 수정

Step 5   백엔드 서버 ──SQLAlchemy(Engine · Session)──▶ Supabase
                                      raw SQL 대신 파이썬 객체로 DB 조작

Step 6   백엔드 서버 를 profiles/ · education/ · auth/ 로 재구성 + 다크모드 화면
                                      기능이 늘어도 안 흔들리는 구조 잡기

Step 7   pytest ──▶ TestClient ──▶ 임시 데이터베이스 ──▶ 테스트 리포트
                                      지금까지 쌓은 것들을 자동으로 확인
```

각 줄의 왼쪽은 "무엇과 무엇을 이었는가"(구성요소·데이터 흐름), 오른쪽은 "그래서 뭐가 되는가"(그 스텝의 목표)입니다. 스텝이 내려갈수록 화살표 가운데(백엔드 서버 안쪽)가 점점 정교해지고, 화살표 양 끝(브라우저·Supabase)은 크게 바뀌지 않는다는 게 이 시리즈 전체를 관통하는 흐름입니다.

각 스텝을 진행할 때는 후속 단계의 작업내용을 미리 적용하지 않고, 반드시 계획상의 해당 스텝에서 다루는 내용만을 충실하게 진행하여야 합니다.

---

## Step 1 — 백엔드와 데이터베이스 연결

- **이 단계의 목표** — 구현한 파이썬 서버가 Supabase DB와 실제로 통신하는지 눈으로 확인하는 것이 목표
- **완성된 모습** — `/health` 호출 시 DB 버전 정보가 JSON으로 응답되는 최종 결과를 확인
- **파일 구조와 작업 위치** — backend 폴더 구조와 `.env`를 두는 이유
- **처음부터 따라 하기** — Supabase 프로젝트 생성부터 서버 실행까지

  **예제 프롬프트**
  ```
  스텝 1은 미니멀한 파이썬 서버가 supabase 데이터베이스에 실제로 연결되는 것을 확인하는 것이 목표.

  다음 요소를 이용해서 `backend` 디렉토리에 백엔드 프로젝트를 초기화하기
  - python
  - fastapi
  - supabase (postgresql, session pooler) + pshycopg 동기호출

  다음 요소를 고려하여 작업하기
  - `/health` 호출 시 supabase 에서 제공하는 데이터베이스의 상태와 버전 정보를 json 형식으로 돌려줌
  - 구현체는 main.py 파일 하나로 통합
  - 필요한 데이터베이스 접속 정보, 크리덴셜은 .env 파일로 두고 서버 실행 시 이 파일로부터 로드하도록 함
  - 필요한 디펜던시는 pip requirements.txt 파일로 정리

  이 단계를 포함하여 앞으로 작업할 모든 엔드포인트에는 해당 엔드포인트의 기능과 이 기능 수행에 필요한 데이터에 대한 설명이 충분하게 제공되어야 함.
  ```

- **보안 체크리스트** — `.env` 노출 방지 등 비밀번호·접속정보 관리 체크리스트

## Step 2 — 테이블을 만들고 API로 읽기

- **이 단계의 목표** — 내가 DB에 넣은 데이터가 웹 주소로 그대로 나오게 만드는 것이 목표
- **완성된 모습** — `/profile` 호출 시 이름과 한 줄 소개가 JSON으로 나오는 결과를 미리 확인
- **`/profile` 주소 만들기** — AI 프롬프트로 GET `/profile` 엔드포인트 코드를 테이블보다 먼저 작성

  **예제 프롬프트**
  ```
  스텝 2는 내가 DB에 넣은 데이터가 서버를 거쳐 그대로 나오게 만드는 것이 목표.

  백엔드 서버에 DB에 저장된 사용자 정보를 돌려주는 엔드포인트를 추가.
  `GET /profile`:
  - 응답에는 이름, 한 줄 소개, 상세 소개, 마지막 업데이트 시각이 포함되어야 함
  - sql query를 직접 쓰는 간단한 방식으로 구현

  필요한 데이터 모양에 맞게 데이터베이스 테이블을 만드는 SQL 을 출력하고 내가 실행할 수 있도록 가이드.
  ```

- **테이블 만들기** — 엔드포인트가 요구하는 컬럼 모양에 맞춰 profile 테이블 SQL을 작성
- **바깥에서 못 보게 잠그기** — RLS 활성화와 권한 회수로 테이블을 외부에서 접근하지 못하게 잠금

## Step 3 — 화면 붙이기 (프론트엔드)

- **이 단계의 목표** — JSON 데이터를 사람이 보는 이력서 페이지로 만드는 것이 목표
- **시작 전 확인** — Node.js와 npm이 설치되어 있는지 버전을 먼저 확인
- **React 프로젝트 만들기** — Vite로 React + TypeScript 프론트엔드 프로젝트를 새로 생성. 이후 남은 네 조각(②~⑤)은 AI 코딩 에이전트에게 준 프롬프트로 진행

  **예제 프롬프트**
  ```
  스텝 3은 스텝 2에서 나오던 생 데이터를 사람이 보는 이력서 페이지로 만드는 것이 목표임

  `frontend` 디렉토리에 다음 기술스택을 갖는 프론트엔드 프로젝트 초기화.
  - Typescript 기반 React SPA 프론트엔드
  - Vite 빌드, 개발서버

  백엔드(FastAPI)가 제공하는 프로필 데이터를 사람이 보는 이력서 화면으로 표시하는 기능을 미니멀하게 구현.
  - 개발 중에는 Vite 프록시로 `/api`로 시작하는 요청을 BE에 그대로 전달
  - BE 응답은 Pydantic DTO로 스키마를 정의하였음. 이 OpenAPI 스펙(`/openapi.json`)에서 TS 타입을 자동 생성하고 프론트엔드에서는 이 타입만을 이용하여야 함
  - `openapi-typescript`를 `npx`로 실행할 수 있도록 환경을 구성하고, 실행은 반드시 나에게 요청하도록 함
  - BE가 데이터베이스에서 읽어와서 제공하는 이름, 한 줄 소개, 상세 소개, 마지막 수정 시각을 화면에 표시
  ```

- **프록시로 백엔드 연결하기** — Vite 프록시로 `/api` 요청을 백엔드로 넘겨 CORS 없이 연결
- **Pydantic DTO와 타입 자동 생성** — Pydantic DTO로 OpenAPI 스펙을 만들고 TS 타입을 자동 생성해 사용

## Step 4 — 로그인, 페이지에서 데이터 수정하기

- **이 단계의 목표** — Supabase 대시보드 없이 웹 화면에서 직접 이력서를 고치는 것이 목표.

  **예제 프롬프트**
  ```
  스텝 4에서는 Supabase에 있는 데이터(profile) 수정을 FE 웹 페이지를 통해서 할 수 있도록 BE와 FE를 확장하는 것임.

  - BE: 비밀번호로 세션 기반 로그인 구현. 관리자 전용 기능은 로그인 상태에서만 가능.
    - 인증 엔드포인트 구현: 로그인, 로그인 상태 확인, 로그아웃 (`itsdangerous` 이용)
    - 프로필 수정 엔드포인트 (PUT)
    - id, 수정 시각은 서버가 데이터 수정 시 자동으로 저장하도록 함
  - FE: 별도 편집 페이지 없이, 보고 있던 이력서 화면 그대로에서 로그인 후 in-place edit
    - 로그인 성공하면 프로필 페이지 자체가 편집 모드 전환. 저장, 로그아웃 기능 추가
    - 로그인이 풀린 상태로 저장을 시도하면 로그인 화면으로 안내
    
  기존 화면(비로그인 상태의 프로필 보기)은 그대로 동작해야 함.
  ```

- **완성된 모습** — 로그인하면 같은 화면이 그대로 제자리 편집 모드로 바뀌는 결과를 확인
- **백엔드 — 로그인과 수정 엔드포인트** — 세션 로그인 3종 엔드포인트와 PUT `/api/profile` 수정 엔드포인트 구현
- **프론트엔드 — 화면은 어떻게 그려지는가** — 로그인 상태에 따라 읽기 화면과 편집 화면을 전환하는 로직 구현

## Step 5 — ORM 도입

- **이 단계의 목표** — raw SQL 대신 파이썬 클래스로 데이터베이스를 다루게 만드는 것이 목표.

  **예제 프롬프트**
  ```
  스텝 5에서는 raw SQL 대신 엔티티 클래스를 통하여 데이터베이스 오퍼레이션을 다루게 만드는 것이 목표임.

  벡앤드에 SQLAlchemy를 도입하여 데이터 접근 방식을 바꾸려고 함.
  - 마이그레이션과 스키마 관리는 불필요함.
  - 현재의 테이블 정의를 파이썬 엔티티 클래스를 만들어서 이전
  - 서버가 시작할 때 엔티티 기준으로 없는 테이블은 자동 생성하고 새 테이블은 비어있으니 초기 데이터 1건을 insert
  - 기존에 구현된 기능들의 데이터베이스 접근을 raw SQL 대신 ORM 호출로 교체
  - API의 주소와 응답 모양(OpenAPI 스펙)은 그대로 둠
  - db.py, models.py, schemas.py 로 구현 내용을 적절히 분리하여야 함
  ```

- **ORM 이 뭐고, 왜 쓰나** — ORM 개념을 소개하고 얻는 것과 잃는 것을 솔직하게 비교
- **설치 · 파일 분리 · 엔티티 정의** — SQLAlchemy를 설치하고 `db.py` / `models.py` / `schemas.py`로 파일 분리
- **테이블 자동 생성과 seed** — 서버 시작 시 테이블을 자동 생성하고 없으면 초기 데이터 1건을 입력
- **엔드포인트를 ORM 으로** — 엔드포인트의 raw SQL 쿼리를 전부 ORM 호출로 교체
- **정리** — 최종 파일 구조를 정리하고 프론트엔드가 영향받지 않았음을 확인

## Step 6 — "이력서" 기능 추가

- **이 단계의 목표** — 지금까지 만든 웹 애플리케이션의 뼈대 위에 이력서라는 애플리케이션의 이름에 맞는 기능을 간단하게 추가함

  **예제 프롬프트**
  ```
  스텝 6에서는 지금까지 만든 프로젝트 구조 위에 다음의 기본적인 이력서 기능을 추가해볼 것임.

  - profile: Read + Update
  - education: Create + Read + Update + Delete

  프론트엔드, 백엔드 모두 package-by-feature 규약을 잘 준수하도록 기존의 프로젝트 구조를 다듬고,
  기능과 각 기능을 구성하는 애플리케이션의 레이어가 잘 보이도록 구현하여야 함.

  앞으로 데이터 모델이 추가될 수 있으므로 기능별 패키지에 models 디렉토리를 만들고 그 안에 모델을 분리하여 구현.

  지금 상태로는 이력서라 부르긴 힘든 스타일이므로 다음과 같은 최소 디자인 요구사항 적용:
  - shadcn 스타일의 미니멀한 UI 스타일
  - 테마 변경 (light/dark 모드 변경) 토글 추가
  - 폰트는 Noto Sans KR로 통일
  - 이모지 및 그라데이션 사용 금지
  ```

- **package-by-feature?** — 애플리케이션 패키징 방식에 대한 설명
- **웹 애플리케이션의 일반적인 구조** — 웹 애플리케이션 서버를 구성하는 계층을 간단하게 살펴봄
- **구현된 기능들** — 구현된 feature와 그 구조를 package-by-feature에 비추어 설명
- **디자인 요소** — 밋밋했던 페이지를 그럴듯하게 만들어준 요소들

## Step 7 — 테스트 추가 (백엔드)

- **이 단계의 목표** — 지금까지 쌓아온 기능들 밑에, 언제 있을지 모르는 소리 없는 무너짐을 대신 알아채 줄 안전망을 깔아두는 것

  **예제 프롬프트**
  ```
  스텝 7에서는 백엔드에 구현된 기능들을 테스트할 수 있는 pytest 기반 테스트를 간단하게 작성할 것임.

  지금 작성하는 테스트의 목적은 테스트 자산이 들어갈 폴더 구조를 확보하고 테스트에 의한 리포트를 볼 수 있게 하는 데 있음.

  다음 사항에 주의할 것.
  - 원본 소스코드는 고쳐서는 안 됨
  - .env에 설정된 실제 데이터베이스는 사용 금지

  테스트 작성을 마치고 테스트 실행방법과 리포트를 볼 수 있는 방법을 가이드.
  ```

- **테스트 전용 환경 만들기** — 실제 `.env` DB 대신 임시 데이터베이스를 사용하고, 테스트마다 스키마를 초기화하는 `conftest.py` 픽스처
- **기능별로 나뉜 테스트 파일** — `test_health.py` / `test_auth.py` / `test_profile.py` / `test_education.py` — package-by-feature 구조를 테스트에도 그대로 반영
- **실행 방법과 커버리지 리포트 보기** — `pytest` 실행 방법과, `pytest-cov`가 만들어주는 `htmlcov/` 리포트를 확인하는 방법
