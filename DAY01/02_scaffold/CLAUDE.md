# Backend

## API 문서화 요건
- 모든 라우터에 `prefix`와 `tags`를 지정해서 OpenAPI 그룹핑이 되도록 한다.
- 모든 엔드포인트에 `response_model`을 명시한다.
- 엔드포인트 함수/파라미터 이름은 그 자체로 의도가 드러나도록 짓는다.
- docstring은 그 이름과 행위가 아주 자명한 경우가 아니라면 항상 추가한다.

## 스키마 요건
- 요청 DTO와 응답 DTO를 분리한다.
- 같은 모델을 요청과 응답 양방향으로 재사용하지 않는다.
- 모든 필드에는 간단한 설명이 있어야 한다.

## 함수/서비스 로직 문서화 요건
- 함수는 이름과 타입 힌트로 대부분의 의도를 전달한다. docstring이 필요한 경우:
  - 도메인 규칙이 코드만으로 유추 불가능할 때 (예: "왜 이 순서로 검증하는지")
  - 외부 시스템(Supabase, 세션 정책)과의 암묵적 계약이 있을 때
- 타입 힌트를 모든 함수 시그니처에 필수로 작성한다.

## 일반 개발 유의사항
- 비밀값(`SESSION_SECRET_KEY`, DB 접속정보 등)은 `.env`로만 관리하고 커밋하지 않는다. `.env.example`을 항상 최신 상태로 유지한다.
- 새 의존성 추가 시 `requirements.txt`(런타임) / `requirements-dev.txt`(개발·테스트 전용)를 구분해서 기입한다.
- 커버리지 리포트는 커밋하지 않는다.

# Frontend

## API/스키마 문서화 요건
- 백엔드 타입은 직접 손으로 작성하지 않는다. 백엔드에서 제공하는 openapi 스펙에 따라 생성하여 사용한다.
- API 함수 이름은 동사+명사로 의도를 드러낸다. 반환 타입은 항상 명시적으로 지정한다.
- 엔드포인트 경로 문자열은 `api.ts` 안에서만 등장해야 하며, 컴포넌트/훅에서 직접 URL을 만들지 않는다.

## 함수/훅 문서화 요건
- 함수/훅 이름과 타입 시그니처로 의도가 드러나야 한다. 주석은 다음의 경우에 반드시 추가한다.
  - 렌더링 타이밍이나 effect 의존성 배열의 이유가 비직관적일 때
  - 브라우저/서드파티 API의 알려진 제약을 우회하는 코드일 때

## 일반 개발 유의사항
- `strict` TypeScript를 유지하고 `any`를 쓰지 않는다. 생성된 스키마 타입을 최대한 활용한다.
- 폼 제출/네트워크 요청 등 사용자 액션은 로딩·에러 상태를 다루도록 한다. 단, 발생 불가능한 상태에 대한 방어 코드는 추가하지 않는다.
- 스타일은 컴포넌트 스코프 CSS 파일을 우선하고, 전역 스타일(`index.css`, `App.css`)에는 실제로 전역인 규칙만 둔다.
